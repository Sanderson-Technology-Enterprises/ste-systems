# STE Systems app audit

Date: October 19, 2026

Scope: current local application, including the unpublished copy, spacing, and client-systems changes

Baseline: `50ab7fe8b7703cf62ba0eab59ad1af51c33df0b4` plus the existing working-tree changes

Environment: production Pages build at `http://127.0.0.1:4185/ste-systems/`, Chromium

## Assessment

The app has a sound foundation. The primary pages render correctly, the tested layouts stay within the viewport, and the main configuration and guide flows work. The recent copy and padding changes make the site easier to read. No critical failure was identified within this audit's scope.

The highest-value next step is reducing unnecessary asset weight. The next priorities are two accessibility details, making all four guides discoverable on phones, and making the client-service path easier to find. The site currently explains its CSS libraries more prominently than the wider application toolkit and services.

This is an audit report, not an implementation. No application code, dependencies, settings, commits, or deployments were changed during this review.

### A1. Serve a display-sized logo

The shared logo is **1,087,286 bytes**, at **1448 × 1086** pixels. The desktop header displays it at **64 × 48** pixels, with a smaller mobile slot. Both the header and footer use the same source. Reusing it benefits from caching, but its first download is unnecessarily large for these slots.

The source is selected in `app/lib/site.ts:24` and rendered by `app/components/SiteHeader.tsx:54` and `app/components/SiteFooter.tsx:18`. The asset builder generates several icon sizes but the site lockups still reference the large source image.

**Recommendation:** generate suitably sized header/footer variants from the original artwork, retain transparency, and use responsive image candidates. Keep the original available for uses that need its resolution.

**Acceptance:** verify sharpness at 1× and 2× display density, preserve the logo's proportions, and substantially reduce the first-download bytes. Set the final budget after comparing actual visual quality; do not trade legibility for an arbitrary number.

### A2. Correct the configuration button's popup semantics

`app/components/LabConfigurationMenu.tsx:60` sets `aria-haspopup="true"`. The controlled panel is a generic container containing a form, not a menu. Runtime inspection confirmed that the panel has no menu role.

WAI-ARIA defines `true` as equivalent to `menu`; the declaration therefore does not match the content opened by the button. See the [WAI-ARIA aria-haspopup definition](https://www.w3.org/TR/wai-aria-1.2/#aria-haspopup).

**Recommendation:** preserve the current disclosure behavior and use its existing `aria-expanded`/`aria-controls` relationship without the inaccurate menu declaration. A dialog would require a deliberate change to semantics and focus behavior, not just another attribute.

**Acceptance:** inspect the accessibility tree and exercise opening, tabbing through the form, Escape, and focus return. Confirm the result with a screen reader; this audit did not test spoken output.

### A3. Make every copy action produce fresh feedback

`app/components/guides/GuideCode.tsx:21` sets the same `"Copied."` string after every successful copy. The second click copied the source successfully, but a MutationObserver recorded **zero changes** inside the status region.

The clipboard operation works. The issue is that repeated success does not produce a new live-region update, which can leave assistive-technology users without fresh confirmation. The Lab already has a revision-based announcement mechanism in `app/components/LabExperience.tsx` that provides a useful implementation pattern.

**Recommendation:** give each result a fresh announcement while retaining concise visible feedback and the existing manual-copy fallback.

**Acceptance:** two consecutive successful copies each produce observable announcement updates; repeat the failure branch as well. Confirm actual announcements with a screen reader rather than relying only on DOM mutations.

### A4. Make all four guides discoverable on phones

At 390px, the tab strip has **336px of visible width** and **711px of scrollable content**. Layout and UI are visible initially. The Interactive tab extends beyond the visible area, and React begins around x=586px. The horizontal scroll behavior is valid and the tabs work, but there is little visual indication that two more guides are available.

The relevant composition is in `app/styles/atlas.css:47`. See the [phone screenshot](../output/app-audit/components-phone.png).

**Recommendation:** retain the installed tab component and add a clear overflow affordance, or use a compact two-row arrangement at phone widths. Preserve logical keyboard order and selected-tab visibility.

**Acceptance:** a first-time phone user can identify all four choices without guessing that the strip scrolls; keyboard selection brings the active tab into view without moving focus elsewhere.

### A5. Bring the client-service path closer to the introduction

The dedicated Customized Platforms/company links begin approximately **4,989px down the page at 390 × 844**, nearly six initial viewport heights. On desktop they begin approximately **2,777px down the page**. The hero actions lead to the Lab and component guides.

That is effective for developers investigating CSS libraries, but a prospective client has to travel farther to understand how the toolkit relates to commissioning an application. The existing links are present; this is a discoverability opportunity, not a missing-link defect.

**Recommendation:** add a concise service-oriented path near the introduction and connect it to the existing client-systems section or Customized Platforms. Keep the technical exploration path prominent. A small public-safe diagram or a concrete example of how the tools support a client workflow could also clarify their relationship.

**Acceptance:** the opening screen or immediately following content offers a clear next step for both developers and prospective clients. Do not imply that this website runs on STE-Core or STE-SDK, and do not expose private project internals.

### A6. Reduce stylesheet weight on fixed-presentation pages

The shared package CSS chunk is **2,488,030 bytes uncompressed**. Local compression estimates are **427,157 bytes gzip** and **293,952 bytes Brotli**. Two additional CSS chunks total about 108KB uncompressed. The homepage, guides, and health page inherit the application-entry stylesheet even though their visual presentation is fixed.

This is a measured optimization opportunity, not proof of poor real-user performance. No throttled performance trace, production transfer encoding, or field timing was measured.

The stylesheet import is at `app/layout.tsx:4`. The installed React package exposes a single aggregate stylesheet entry point; a supported smaller entry point was not found in its export map.

**Recommendation:** first measure production performance, then investigate an upstream-supported preset-specific stylesheet or route-aware loading strategy. Preserve the full configurability of the Lab and the libraries' ownership boundaries. Do not manually cut arbitrary rules out of generated CSS.

**Acceptance:** compare cold-load bytes, rendering, focus/state styling, and all configured Lab presets before and after any change. Keep package imports documented and supported.

### A7. Allow the Lab to demonstrate native preset palettes

The palette selector offers 25 named themes and no native/default option. `LabExperience.tsx:268` always emits `data-theme`. The configuration type and parser likewise require a named theme. Meanwhile, the guide explains that omitting `data-theme` uses a preset's native palette, and the combination model counts a native palette for each preset in `app/data/atlas.ts:83`.

The combination count describes library capability; this finding does **not** establish that the arithmetic is wrong. It establishes that one documented capability cannot currently be selected through the Lab controls.

**Recommendation:** support an explicit “Preset default” choice that omits `data-theme`, including in copied markup, saved configuration, shared URLs, reset behavior, and the integration preview.

**Acceptance:** select a preset default, reload, share the URL, and inspect copied markup. The native palette remains selected consistently. Treat this as a separate Lab enhancement; it was not implemented in this audit.

### A8. Improve small labels and remove duplicated vertical spacing

The mobile brand-owner line computes to **8px**. Homepage eyebrow/section labels compute to **11.2px**. These values are not automatically accessibility violations, but the long legal-name line is difficult to read at its current size.

The client-systems introduction also has a **120px gap** from the last paragraph to the first card row at 1440px. Its heading contributes a **48px bottom margin**, while the parent stack contributes a **64px gap**. The two spacing mechanisms accumulate.

**Recommendation:** simplify the header lockup or provide more readable attribution while retaining the full company name elsewhere. Let one mechanism own the gap between section introductions and their content. Preserve the comfortable panel insets added in the recent patch.

**Acceptance:** review phone and desktop screenshots at normal zoom and enlarged text. The attribution remains readable, and sections feel connected without returning text to panel edges.

### A9. Provide a resilient documentation fallback

With JavaScript disabled, loading `/components/#atlas-react` still shows only the Layout panel. The other tab controls are rendered but cannot reveal their guides. This was reproduced with a separate browser context; the normal JavaScript-enabled flow works.

**Recommendation:** consider addressable guide pages, progressively enhanced anchor navigation, or a readable no-JavaScript fallback. This is most useful for documentation reliability when hydration or script delivery fails; it is not a request to remove interactivity.

**Acceptance:** the four guides remain readable through an explicit fallback when scripts are unavailable, and the normal tab experience remains unchanged.

## Suggested delivery order

1. **Small targeted fixes:** right-size the logo, correct configuration semantics, and refresh repeated-copy feedback. Verify each change with its own focused check.
2. **Visitor experience:** improve mobile tab discovery, add an earlier service path, and adjust small labels/duplicated spacing. Review phone, tablet, and desktop screenshots.
3. **Separate technical enhancements:** evaluate stylesheet delivery, native-palette configuration, and documentation fallback. These require their own scope and compatibility checks.

For a future implementation, retain the current four-guide model, base-path-aware links, private repository boundaries, fixed non-Lab presentation, and installed STE USK React component layer. No dependency upgrade is necessary merely to begin the first two groups.
